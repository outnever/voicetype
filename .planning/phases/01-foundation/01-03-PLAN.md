实现基于 AVAudioEngine 的实时音频采集（per D-09 AVAudioEngine + 16kHz mono Float32, RESEARCH.md Pattern 5, PITFALLS.md Pitfall 3 预防）：

1. **AudioFormat.swift：**
   ```swift
   import AVFoundation

   enum AudioConstants {
     static let sampleRate: Double = 16000
     static let channels: AVAudioChannelCount = 1
     static let commonFormat: AVAudioCommonFormat = .pcmFloat32
     static let interleaved: Bool = false

     static var audioFormat: AVAudioFormat {
       AVAudioFormat(
         commonFormat: commonFormat,
         sampleRate: sampleRate,
         channels: channels,
         interleaved: interleaved
       )!
     }

     // ~64ms buffer at 16kHz = 1024 frames
     static let tapBufferSize: AVAudioFrameCount = 1024

     // Maximum audio buffer: 30 seconds at 16kHz
     static let maxBufferCapacity: Int = Int(sampleRate) * 30
   }
   ```
   - 提供 `currentInputDeviceName` 辅助属性（从 `AVAudioSession.sharedInstance().currentRoute` 读取）

2. **AudioBuffer.swift（环形缓冲区）：**
   - `final class RingBuffer<Element>`，泛型支持
   - 使用 `os_unfair_lock` 保护线程安全（单生产者（audio tap 线程）× 单消费者（VAD/转写线程）模式，`os_unfair_lock` 比 `DispatchQueue` 延迟更低）
   - `init(capacity: Int)` —— 分配固定容量
   - `func write(_ elements: [Element])` —— 追加数据，缓冲区满时覆盖旧数据
   - `func read(count: Int) -> [Element]` —— 读取指定数量（不清除）
   - `func consume(count: Int)` —— 消耗指定数量（读取后清除）
   - `var availableCount: Int` —— 可读采样数
   - `func reset()` —— 清空缓冲区
   - **禁止在 write/read 中做内存分配**（实时音频线程要求）

3. **AudioCaptureService.swift（per RESEARCH.md Pattern 5 完整实现）：**
   - `final class AudioCaptureService: @unchecked Sendable`
   - 属性：`private let engine = AVAudioEngine()`、`private let buffer = RingBuffer<Float>(capacity: AudioConstants.maxBufferCapacity)`、`private var isConfigured = false`

4. **`func start() throws`（per D-09 + Pattern 5）：**
   - 获取 `let inputNode = engine.inputNode`
   - 获取硬件格式：`let inputFormat = inputNode.outputFormat(forBus: 0)`
   - 创建格式转换器：`guard let converter = AVAudioConverter(from: inputFormat, to: AudioConstants.audioFormat) else { throw AudioError.formatConversionFailed }`
   - 安装 tap：
     ```swift
     inputNode.installTap(onBus: 0, bufferSize: AudioConstants.tapBufferSize, format: inputFormat) { [weak self] pcmBuffer, _ in
       guard let self else { return }
       // 转换到目标格式
       let targetCapacity = AVAudioFrameCount(Double(pcmBuffer.frameLength) * (AudioConstants.sampleRate / inputFormat.sampleRate))
       guard let convertedBuffer = AVAudioPCMBuffer(pcmFormat: AudioConstants.audioFormat, frameCapacity: targetCapacity) else { return }
       var error: NSError?
       let inputBlock: AVAudioConverterInputBlock = { _, outStatus in
         outStatus.pointee = .haveData
         return pcmBuffer
       }
       converter.convert(to: convertedBuffer, error: &error, withInputFrom: inputBlock)
       if error == nil, let floatData = convertedBuffer.floatChannelData {
         let frames = Int(convertedBuffer.frameLength)
         let samples = Array(UnsafeBufferPointer(start: floatData[0], count: frames))
         self.buffer.write(samples)
       }
     }
     ```
   - `try engine.start()` —— 启动引擎
   - **关键——禁止在 tap 回调中做任何处理**（per RESEARCH.md Anti-Patterns）：回调仅做格式转换 + 写入环形缓冲区。不做 logging、不做 VAD、不做 level metering。
   - 错误定义：`enum AudioError: Error { case formatConversionFailed, engineStartFailed, tapAlreadyInstalled }`

5. **`func stop()`：**
   - `engine.inputNode.removeTap(onBus: 0)`
   - `engine.stop()`
   - `buffer.reset()`

6. **辅助方法：**
   - `var isRunning: Bool` —— `engine.isRunning`
   - `func readSamples(count: Int) -> [Float]` —— 从 RingBuffer 读取（暴露给未来 VAD/WhisperKit）
   - `func currentDeviceDescription() -> String` —— 返回当前输入设备名

7. **编译验证：** Build 成功。`AudioCaptureService.start()` 可被调用。

实现音频设备变更的自动检测与处理（per D-10 热插拔监控, RESEARCH.md Pitfall 3 预防, AUDI-02）：

1. **设备监控方法 `func startDeviceMonitoring()`（per RESEARCH.md 音频设备路由变更代码示例）：**
   - 监听 `Notification.Name.AVAudioEngineConfigurationChange`（引擎内部配置变更——格式/采样率变化）：
     - 在 handler 中：如果 `engine.isRunning`，移除旧 tap → 重新 `start()`（安装新格式的 tap）→ 发送设备变更通知
   - 监听 `AVAudioSession.routeChangeNotification`（硬件路由变更——设备插拔）：
     - 解析 `notification.userInfo?[AVAudioSessionRouteChangeReasonKey]`
     - `.oldDeviceUnavailable`：当前设备被拔出 → 重新 `start()`（引擎自动切换到系统默认设备）
     - `.newDeviceAvailable`：新设备插入 → 重新 `start()`（可选切换）
   - **处理模式**：stop → start 而非原地修改（PITFALLS.md Pitfall 3 推荐方式，避免旧格式残留）

2. **静音检测（额外安全层，per Pitfall 3）：**
   - `func startSilenceDetection(threshold: Float = 0.001, duration: TimeInterval = 5.0)` 
   - 定时器定期从 RingBuffer 读取最近 N 个采样，计算 RMS 能量
   - 如果 RMS < threshold 且持续 > duration 秒 → 可能存在无声故障（麦克风未连接、权限被撤销但未报错等）
   - 通过 `Notification.Name.audioSilenceDetected` 通知 AppCoordinator

3. **AppCoordinator 集成（修改 AppCoordinator.swift）：**
   - 在 AppCoordinator 中添加 `let audioCapture = AudioCaptureService()` 实例
   - 添加 `@Published var currentInputDevice: String = "Unknown"`
   - 监听 `Notification.Name.audioDeviceChanged` → 更新 `currentInputDevice` 和 `statusMessage`
   - 监听 `Notification.Name.audioSilenceDetected` → 在 `statusMessage` 中显示 "注意：麦克风可能未工作"
   - 在异步初始化块中调用 `audioCapture.startDeviceMonitoring()`（设备监控独立于音频采集运行，始终监听）
   - **提供 `func startAudioCapture() throws` 和 `func stopAudioCapture()`** —— 委托给 AudioCaptureService，供 Phase 2 的 AppCoordinator 热键回调使用

4. **扩展 Notification.Name：**
   在 AudioCaptureService.swift 或 AppCoordinator.swift 中定义：
   ```swift

     static let audioDeviceChanged = Notification.Name("com.voicetype.audio.deviceChanged")
     static let audioSilenceDetected = Notification.Name("com.voicetype.audio.silenceDetected")
   }
   ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| 麦克风硬件 → AVAudioEngine input node | 原始音频数据从硬件驱动进入应用进程 |
| Audio tap 回调线程 → RingBuffer | 实时音频线程写入环形缓冲区——不可阻塞 |
| RingBuffer → 消费者（Phase 2 VAD/WhisperKit） | 采样数据从缓冲区读出供下游处理 |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-10 | Denial of Service | AudioCaptureService.swift | high | mitigate | 设备拔出时（`oldDeviceUnavailable`）自动 stop→start 切换到默认设备（D-10, AUDI-02）。AVAudioEngine 内部崩溃或 tap 失活时，`AVAudioEngineConfigurationChange` 监听器触发重新配置。静音检测（5 秒持续低能量）作为兜底告警。所有错误路径（formatConversionFailed, engineStartFailed）向 AppCoordinator 报告，菜单栏可见。 |
| T-01-11 | Information Disclosure | AudioCaptureService.swift | medium | mitigate | 音频采样仅写入内存中的 RingBuffer——不落磁盘文件（PITFALLS.md Security Mistakes）。Info.plist 已声明 `NSMicrophoneUsageDescription` 告知用户录音用途。Phase 1 仅采集不处理（无转写、无网络发送），audio tap 数据仅存于进程内存。菜单栏图标反映录音状态（Phase 2 实现，Phase 1 预留路径）。 |
| T-01-12 | Denial of Service | AudioCaptureService.swift | medium | mitigate | tap 回调在实时音频线程执行——仅做格式转换 + `RingBuffer.write`（O(1) 操作，无内存分配）。禁止在回调中做 logging、VAD 处理、format probling（per RESEARCH.md Anti-Patterns）。RingBuffer 使用 `os_unfair_lock`（非阻塞锁，比 DispatchQueue 快且不引起优先级反转）。缓冲区溢出时覆盖旧数据而非崩溃。 |
| T-01-13 | Information Disclosure | RingBuffer<Float> | low | accept | 内存中的原始 PCM 数据以 Float32 数组存储。攻击者需要进程内存读取权限才能访问——在此权限级别下可获取的信息远超音频数据。风险低——应用在 Phase 1 不将音频发送到任何外部服务。Phase 2 将增加 buffer 清理逻辑（每次听写结束后 `buffer.reset()`），但 Phase 1 仅做基础采集管线。 |
</threat_model>
